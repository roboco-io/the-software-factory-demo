# 정책 기반 자동 포스트모템 설계

작성일: 2026-10-21. 근거: 2026-10-21 사용자 인터뷰와 같은 날 진행한 #66 장애 분석. 상위 설계: `docs/superpowers/specs/2026-10-11-software-factory-design.md`(이하 "팩토리 설계").

## 1. 목적과 배경

### 1.1 왜 만드는가

2026-10-13 22:20Z에 팩토리가 사이트 이름 변경 PR #65(요청 이슈 #63)를 병합했다. 이 변경은 프로덕션 스모크의 홈 heading 기대값(`conduit`)을 깼다. 그런데 스모크 파일은 T3 경로이므로 구현 에이전트가 고칠 수 없었다. 22:52Z부터 정기 스모크가 실패했고, 스모크 이슈 #66에는 "복구 없이 N회째" 코멘트만 27번 달렸다. 사람이 원인을 진단한 것은 2026-10-21이다. 약 8일 동안 원인을 아는 주체가 없었다.

같은 기간에 주간 자기개선이 반복 실패를 개선 후보로 골라 개선 PR #72를 만들었다. 그러나 스모크 이슈에는 실패 원문이 없었다. 그래서 개선 에이전트는 원인을 추정했고, 그 추정은 틀렸다. 실제 원인과 반대 방향의 규칙("스모크가 의존하는 화면 요소를 바꾸지 말라")을 제안했고, #72는 닫혔다.

이 설계의 목적은 하나다. 프로덕션 장애와 팩토리 정체가 원인을 모르는 채 길어지지 않게 한다. 이를 위해 팩토리는 장애를 처음 감지한 즉시 사실을 수집하고 원인을 분석한다. 원인 PR을 근거로 확신하면 되돌려서 먼저 복구한다. 복구한 뒤에는 재발 방지책을 PR로 제안한다. 이 동작 전체를 정책 파일이 정한다. 사람은 정책 파일을 바꿔 동작을 조정한다.

### 1.2 성공 기준

#66을 이 정책으로 재생했을 때 다음이 일어나면 성공이다. 첫 실패 스모크 직후 분석이 시작된다. 분석은 #65를 원인 PR로 특정하고, 근거로 실패 원문(홈 heading `conduit` 미검출. 당시 스모크는 옛 이름을 기대했다)과 #65의 변경 파일(홈 heading을 그리는 `apps/web/src/pages/Home.tsx`, `Header.tsx`, `Footer.tsx`, `index.html`)을 제시한다. #65의 변경 파일은 T1이므로 되돌리기 PR이 자동 병합된다. 되돌리기 배포의 스모크가 성공하면 복구로 기록되고 #63이 다시 열린다. 사후 분석은 오늘 사람이 내린 진단(T3 계약이 갱신되지 않음, `e2e-preview`가 필수 체크가 아님, 스모크 이슈에 원문 없음)과 같은 결론을 내고, 개선 PR을 연다. 재생 방법은 7절에 있다.

### 1.3 목표·비목표·반목표

목표는 네 가지다. 첫째, 장애 첫 감지부터 원인 진단까지의 시간을 분석 1회 소요 시간 수준으로 줄인다. 둘째, 원인이 확실한 회귀는 사람 없이 복구한다. 셋째, 장애마다 근거가 붙은 포스트모템 기록을 이슈와 대시보드에 남긴다. 넷째, 장애마다 재발 방지 개선 PR을 연다.

비목표도 있다. 위험 등급 정책을 우회하지 않는다. 마이그레이션을 되돌리지 않는다. 외부 서비스(Cloudflare, GitHub)의 장애를 고치려 하지 않는다. 스모크 주기(현재 6시간, `factory-smoke.yml`의 `23 */6 * * *`)를 이 설계에서 바꾸지 않는다. 감지 지연은 이 주기만큼 남는다.

반목표는 정책이 동작해도 실패로 보는 상황이다. 인터뷰에서 사용자가 네 가지를 모두 골랐다. 각 반목표에는 대응 장치를 하나씩 둔다.

| 반목표 | 대응 장치 |
|---|---|
| 원인이 아닌 PR을 되돌려 정상 기능을 없앰 | 되돌리기 조건(4.4)의 근거 필드 필수, 확신 조건 미충족 시 진단만 |
| 같은 장애를 반복 분석해 비용이 폭주함 | 장애당 분석 횟수 상한과 일일 비용 상한(4.6) |
| 길기만 하고 실행할 내용이 없는 보고서 | 고정 양식과 길이 상한(4.5) |
| 추정을 사실처럼 쓰고 그것으로 개선 PR을 만듦(#72) | 사실·추정 구분 표기, 근거 없는 원인은 개선 PR 입력에서 제외(4.5, 4.7) |

## 2. 확정된 결정 (2026-10-21 인터뷰)

다음은 사용자가 정한 것이다.

1. 분석 시작 시점: 장애가 처음 실패한 즉시. 일시적 실패에 드는 비용은 감수한다.
2. 범위: 봇 PR이 일으킨 장애, 사람 PR이 일으킨 장애, 외부 요인 장애, 팩토리 정체를 모두 다룬다.
3. 팩토리 정체의 기준: 실패성 사유로 이슈가 `factory:needs-human`이 된 경우에만 즉시 시작한다. T2·T3 승인 대기처럼 설계상 사람을 기다리는 경우는 제외한다.
4. 첫 조치: 원인 PR이 특정되면 복구를 우선한다. 원인 PR이 요청대로 작업한 정당한 변경이어도 먼저 되돌리고, 원래 요청 이슈를 다시 연다.
5. 되돌리기의 병합: 되돌리기 PR도 기존 위험 등급 정책(`factory/risk-policy.yml`)을 그대로 따른다. T0·T1이면 자동 병합하고, T2·T3이면 PR을 열고 사람 승인을 기다린다.
6. 불확실할 때: 근거로 원인 PR 하나를 확신할 때만 되돌린다. 그렇지 않으면 진단만 남기고 사람에게 넘긴다.
7. 기록 위치: 장애 이슈에 포스트모템 본문을 남기고, 대시보드에 장애 타임라인과 복구 시간을 보여 준다.
8. 개선 제안: 장애마다 복구 직후 개선 PR을 즉시 연다. 병합은 T3 사람 승인이다.
9. 예산: 수치는 설계자(Claude)에게 맡겼다. 4.6의 기본값은 설계자의 판단이다.

다음은 설계자의 판단이며, 사용자가 확인하지 않았다.

- 정책은 `factory/postmortem-policy.yml` 한 파일에 둔다. 이 경로는 `factory/**`이므로 T3이다.
- 사실 수집은 결정적 코드로 하고, 에이전트는 분석과 서술만 한다.
- 분석 모델 기본값은 리뷰·개선 역할과 같은 Sonnet급(`claude-sonnet-5-5`)이다. 입력이 구조화된 타임라인이고 출력 양식이 고정되어 있어 충분하다고 판단했다. 품질이 부족하면 정책 파일에서 상위 모델로 올린다. 모델 ID는 코드에 쓰지 않는다.
- 되돌리기 PR은 에이전트 없이 `git revert`로 만든다.

## 3. 용어

- **장애(incident)**: 정책이 다루는 하나의 사건이다. 장애 이슈의 실패 회차 하나에 대응한다. `smoke.ts`는 복구 뒤에도 스모크 이슈를 닫지 않고, 다음 실패를 같은 이슈에 코멘트로 붙인다. 그래서 "복구 → 실패" 전이마다 새 장애로 보고, 장애 식별자는 이슈 번호와 회차의 조합이다. 예산(4.6), 포스트모템 기록(4.5), 런 기록은 이 단위로 센다(설계자 판단). 프로덕션 장애는 `source:smoke`, `source:deploy`, `source:error` 이슈이다. 팩토리 정체는 해당 요청 이슈 자체이다.
- **장애 구간**: 마지막 정상 관측과 첫 실패 관측 사이의 시간이다. 스모크라면 마지막 성공 스모크 run과 첫 실패 스모크 run 사이이다.
- **후보 PR**: 장애 구간에 main에 병합되어 프로덕션에 배포된 PR이다. 봇 PR과 사람 PR을 모두 포함한다.
- **원인 PR**: 분석이 4.4의 확신 조건을 모두 충족해 특정한 후보 PR 하나이다.
- **1차 분석**: 장애를 처음 감지한 직후의 분석이다. 목적은 원인 진단과 복구 조치이다.
- **사후 분석**: 복구가 확인된 직후의 분석이다. 목적은 포스트모템 기록 완성과 개선 PR 제안이다.

## 4. 정책

### 4.1 정책 파일

`factory/postmortem-policy.yml`은 아래 항목을 가진다. 형식은 `risk-policy.yml`처럼 Zod 스키마로 검증한다. 값은 이 절의 기본값으로 시작한다.

```yaml
triggers:
  production: [source:smoke, source:deploy, source:error]
  stall:
    # 이 사유로 needs-human이 되면 정체로 본다. 런 기록의 failureReason 값이다.
    reasons: [max_turns, timeout, budget, engine_error, invalid_output, merge_refused,
              smoke_contract, preview_deploy, human_action, unlisted_check, risk_tier,
              too_many_files, skip_txt, review_needs_human]
    # 설계상 사람을 기다리거나 다른 경로가 맡는 사유. 정체로 보지 않는다.
    exclude: [risk_t2, risk_t3, permission_denied, deploy_failed]
revert:
  enabled: true
  reopen_request: true
budget:
  per_incident_analyses: 2      # 1차 1회 + 사후 1회
  per_analysis_usd: 2
  per_analysis_minutes: 15
  daily_usd: 10
report:
  max_chars: 6000
agent:
  role: postmortem              # 엔진·모델은 factory/agents 설정의 역할 배정을 따른다
```

정체 사유 목록은 2026-10-21 main의 `failureReason`과 `stepRecord` 사유를 전수 조사해 확정했다(구현 계획에서 확정한 값이며 초안과 다르다). 정체로 보는 사유는 위 `reasons`이다. `risk_t2`·`risk_t3`·`permission_denied`는 설계상 사람을 기다리는 사유이고, `deploy_failed`는 배포 실패 경로(4.2)가 따로 맡으므로 `exclude`에 둔다. 초안의 `review_failed`는 `review_needs_human`으로 바뀌었다. 리뷰가 에이전트가 고칠 수 없는 지적을 남겨 사람에게 넘기는 경우를 이 사유로 새로 기록한다. 초안에 있던 `publish_failed`·`bundle_rejected`는 사람에게 넘기는 사유가 아니라서 뺐다. `revert.require`(확신 조건)는 정책 파일이 아니라 코드가 고정한다(4.4). 에이전트 역할의 엔진·모델은 `factory/agents.yml`의 `postmortem` 역할이 정한다.

### 4.2 트리거

프로덕션 장애의 1차 분석은 장애 이슈가 처음 만들어질 때 시작한다. 스모크는 `smoke.ts`가 새 `source:smoke` 이슈를 만들거나 닫힌 이슈를 다시 실패 상태로 바꿀 때이다. 같은 장애의 반복 실패 코멘트는 새 분석을 시작하지 않는다. 배포 실패와 프로덕션 오류도 각 단계가 장애 이슈를 처음 만들 때 시작한다.

정체의 1차 분석은 이슈가 `factory:needs-human`으로 옮겨지고 그 런 기록의 사유가 `triggers.stall.reasons`에 있을 때 시작한다. `@factory stop`처럼 사람이 직접 옮긴 경우는 제외한다.

사후 분석은 장애가 복구됐을 때 시작한다. 스모크는 "복구됨" 표식이 남을 때이다. `deploy.yml`의 smoke job은 curl 3개만 실행하고 복구 표식을 남기지 않는다. 그래서 되돌리기 커밋이 배포되면 `runDeployed`가 전체 스모크(`factory-smoke.yml`)를 즉시 dispatch하고, 그 스모크의 기존 복구 경로가 "복구됨" 표식을 남긴다. 정기 스모크 주기(6시간)를 기다리지 않는다는 의도는 같다(구현 계획에서 확정한 방식). 배포 실패는 같은 커밋 계열의 다음 배포가 성공할 때이다. 프로덕션 오류는 이슈가 닫힐 때이다. 정체는 요청 이슈가 `merged` 또는 `deployed`가 되거나 사람이 닫을 때이다.

배포 실패(`runDeployFailed`)는 별도 장애 이슈를 만들지 않고 원인 요청 이슈에 `source:deploy`를 붙여 `needs-human`으로 옮긴다. 이때 원인 PR은 이미 알려져 있고, 배포가 실패했으므로 프로덕션은 대체로 이전 버전에 머문다. 그래서 배포 실패의 1차 분석은 진단만 하고 되돌리지 않는다. 배포가 일부만 반영되어 프로덕션이 실제로 깨졌다면 다음 스모크가 별도 장애로 잡고, 그 장애에서 되돌리기를 판정한다. 같은 이슈가 정체 트리거로도 잡히지 않도록 `deploy_failed`는 정체 사유에서 뺀다(설계자 판단).

프로덕션 오류(`source:error`)는 `type:bug`가 붙어 기존 버그 수정 흐름(트리아지 후 `@factory go`)의 대상이 된다. 포스트모템은 이 흐름을 바꾸지 않는다. 1차 분석이 확신 조건을 충족하면 복구 우선 결정에 따라 먼저 되돌리고, 오류 이슈에는 되돌린 사실을 코멘트로 남긴다. 사람이 그 뒤 `@factory go`를 남기면 기존 흐름대로 수정이 진행된다. 오류 장애의 장애 구간은 해당 fingerprint의 최초 관측 시각 직전 24시간이다(설계자 판단).

트리거는 기존 단계가 상태를 바꾸는 지점에서 `factory-postmortem.yml`을 dispatch하는 방식으로 건다. 구현 방식(dispatch, 이슈 이벤트, 예약 실행)은 구현자가 정한다. 다만 정기 스모크 다음 주기까지 기다리는 방식은 "즉시" 결정에 맞지 않는다.

### 4.3 사실 수집

에이전트를 부르기 전에 코드가 타임라인 JSON을 만든다. 이 JSON이 분석의 유일한 사실 입력이다. 포함할 항목은 다음과 같다.

- 장애 이슈의 생성 시각, 실패·복구 표식, 실패 원문. 스모크 원문은 PR #74가 이슈와 런 기록에 남긴다.
- 장애 구간과 후보 PR 목록. 각 PR의 작성자(봇·사람), 병합 시각, 변경 파일과 위험 등급, 연결 요청 이슈를 넣는다.
- 각 후보 PR의 체크 결과. 필수 체크와 비필수 체크(`e2e-preview`, `smoke-preview` 등)를 모두 넣는다. #65에서 결정적 단서는 비필수 체크 `e2e-preview`의 실패였다.
- 후보 PR과 장애 이슈의 런 기록(gate 판정, 리뷰 판정, 수정 라운드).
- 정체의 경우, 해당 요청의 런 기록 전체와 PR 리뷰 판정 본문.

수집 범위는 장애 구간으로 제한한다. 장애 구간을 정할 수 없으면 첫 실패 직전 24시간으로 한다. 이 24시간은 설계자의 판단이다.

### 4.4 1차 분석과 되돌리기

에이전트는 타임라인을 받아 구조화된 결과를 낸다. 결과에는 분류(봇 PR 회귀, 사람 PR 회귀, 외부 요인, 정체), 원인 PR 번호 또는 없음, 원인마다의 근거 목록, 권장 조치가 들어간다. 근거 항목은 타임라인 안의 사실을 가리켜야 한다. 사실을 가리키지 않는 근거는 추정으로 표시한다.

코드가 이 결과를 받아 되돌리기 여부를 판정한다. 판정은 에이전트가 아니라 코드가 한다. 되돌리기는 다음 조건을 모두 충족할 때만 한다.

1. 분류가 봇 PR 회귀 또는 사람 PR 회귀이다.
2. 원인 PR이 하나이다. 후보 PR이 여러 개이면, 에이전트가 원인 PR 하나를 지목하고 그 근거에 실패 원문과 원인 PR 변경 파일의 대응이 있어야 한다.
3. 근거에 실패 원문의 인용이 있다. 원문이 없는 장애는 되돌리지 않는다(#72의 교훈).
4. 원인 PR의 변경 파일이 실패 원문이 가리키는 영역과 겹친다. 겹침의 판정 방식은 구현자가 정한다. 다만 판정은 결정적이어야 하고 테스트로 고정해야 한다.
5. 원인 PR 이후의 커밋과 되돌리기가 충돌하지 않는다.

조건을 충족하면 코드가 `git revert`로 되돌리기 PR을 만든다. 이 PR에는 팩토리 표식(`role: "revert"`, `issue`: 장애 이슈 번호)을 붙이고, `implementEngine`·`implementModel`에는 1차 분석을 한 엔진과 모델을 적는다. 병합 커밋 메시지는 `Factory-Issue` 대신 `Factory-Revert: #<장애 이슈>` trailer를 쓴다(구현 계획에서 확정). `Factory-Issue` trailer가 없어야 deploy가 상태 전이 대상으로 삼지 않는다. 원인 PR의 요청 이슈는 이미 `deployed`로 닫혀 있으므로 연결 대상이 아니다. gate는 `revert` 역할에 대해 `in-review` 상태 검사를 건너뛰는 분기를 둔다. deploy 단계는 `revert` 역할 커밋의 이슈를 상태 머신으로 옮기지 않고, 장애 이슈에 배포 결과만 코멘트로 남긴다. 이렇게 해야 다시 연 요청 이슈를 deploy가 곧바로 닫지 않는다(설계자 판단). 병합은 기존 gate가 위험 등급에 따라 처리한다. T0·T1은 체크가 통과하면 자동 병합된다. 되돌리기 PR에는 교차 리뷰 승인을 요구하지 않는다. 이것은 설계자의 판단이며, 이유는 복구 우선 결정이다. T2·T3이면 PR을 열고 CODEOWNERS 승인을 기다린다. 원인 PR에 마이그레이션이 있으면 앱 코드 되돌리기는 허용하되 마이그레이션 파일은 되돌리지 않는다. 그런 PR은 T2이므로 어차피 사람이 승인한다.

조건을 하나라도 충족하지 못하면 되돌리지 않는다. 진단을 장애 이슈에 남기고, 장애 이슈를 사람에게 넘긴다.

복구가 확인되면 원인 PR의 요청 이슈를 다시 연다. 다시 연 이슈에는 되돌린 이유와 다시 처리할 때 함께 바꿔야 할 것(예: T3 스모크 갱신)을 코멘트로 남긴다. 다시 연 이슈가 자동으로 구현되지는 않는다. 기존 규칙대로 `@factory go`가 필요하다.

외부 요인과 정체에는 되돌릴 PR이 없다. 1차 분석은 진단과 권장 조치만 남긴다.

### 4.5 포스트모템 기록

포스트모템은 장애 이슈 본문 또는 고정 코멘트 하나에 남긴다. 1차 분석이 초안을 만들고, 사후 분석이 같은 기록을 갱신한다. 코멘트를 계속 늘리지 않는다. 양식은 고정이다.

1. 요약: 무엇이 언제부터 언제까지 어떻게 영향을 주었는가.
2. 타임라인: 감지, 1차 분석, 조치, 복구 시각.
3. 원인: 근본 원인과 근거. 각 문장에 [사실] 또는 [추정]을 표시한다.
4. 막지 못한 방어선: 어느 체크·단계가 왜 잡지 못했는가.
5. 조치와 개선 PR 링크.

전체 길이는 `report.max_chars`를 넘지 않는다. 비난 없는(blameless) 서술을 쓴다. 사람이나 에이전트를 탓하지 않고 구조를 설명한다.

대시보드(`apps/web/factory/`)는 런 기록에서 장애 목록, 장애별 타임라인, 복구 시간(감지부터 복구까지)을 보여 준다. 이를 위해 런 기록에 포스트모템 역할의 레코드를 추가한다. 레코드에는 장애 이슈 번호, 분류, 감지·복구 시각, 원인 PR, 되돌리기 여부를 넣는다. 화면 구성은 구현자가 정한다.

### 4.6 예산

장애당 분석은 최대 2회(1차 1회, 사후 1회)이다. 분석 1회의 상한은 2 USD, 15분이다. 하루 포스트모템 비용의 합계 상한은 10 USD이다. 일일 상한에 도달하면 이후 장애는 분석 없이 사실 수집 결과만 장애 이슈에 남긴다. 이 수치는 설계자의 판단이다. 근거는 분석 입력이 구현보다 작고 코드 변경이 없다는 점이다. 기존 구현 예산(80턴, 30분, 5 USD)의 절반 이하로 잡았다.

같은 장애에서 분석이 실패하면(시간 초과, 출력 형식 오류) 재시도하지 않는다. 사실 수집 결과와 실패 사유만 남긴다.

### 4.7 개선 PR

사후 분석이 끝나면 즉시 개선 PR을 연다. 기존 자기개선 단계(`improve`)를 재사용하고, 입력만 주간 리포트 후보 대신 포스트모템 기록으로 바꾼다. 별도 워크플로를 만들지 않고 `factory-weekly.yml`에 `workflow_dispatch` 입력 `issue`를 더한다. 이 입력이 있으면 report job을 건너뛰고 그 장애 이슈로 improve를 실행한다(구현 계획에서 확정). 후보는 장애 이슈에 `factory:postmortem` 라벨과 후보 표식 코멘트(`factory:postmortem-candidate`)로 남긴다. 개선 PR은 기존처럼 평가 케이스(`factory/evals/`)를 포함하고, T3이므로 사람이 승인한다.

개선 PR의 입력에는 [사실]로 표시된 원인과 막지 못한 방어선만 넣는다. [추정]만 있는 장애에서는 개선 PR을 열지 않고, 기록에 "근거 부족으로 개선 제안 보류"라고 남긴다.

주간 리포트는 포스트모템이 이미 개선 PR을 연 범주를 같은 주에 다시 후보로 내지 않는다.

## 5. 기존 구성과의 관계

- 위험 등급 정책, gate, 교차 리뷰, CODEOWNERS 규칙은 바꾸지 않는다. 되돌리기 PR은 새로운 역할(`revert`)로 gate를 통과한다. gate에서 이 역할을 처리하는 분기가 필요하다.
- 상태 머신(`state/machine.ts`)에 되돌리기와 요청 재오픈을 위한 전이가 필요할 수 있다. 구현자가 확인한다.
- 2026-10-21에 열린 세 PR이 이 설계의 전제다. #73은 T2 PR의 리뷰 수정 라운드, #74는 스모크 실패 원문, #75는 프리뷰 스모크와 `smoke_contract`·`preview_deploy` 사유를 다룬다. 특히 #74가 없으면 4.4의 조건 3을 충족할 수 없다.
- 이 설계 전체는 T3 변경이다.

## 6. 구현자에게 맡기는 것

다음은 구현자가 정한다. 트리거를 거는 방식, 타임라인 JSON의 정확한 스키마, 겹침 판정 방식, 대시보드 화면 구성, 포스트모템 에이전트의 프롬프트 문구(`factory/prompts/postmortem.md`), 정체 사유 목록의 최종 값이 해당된다.

## 7. 검증

단위 테스트는 기존 패턴(메모리 GitHub, 가짜 에이전트 어댑터)을 따른다. 되돌리기 판정은 조건별로 충족과 미충족 사례를 모두 테스트한다.

#66 재생은 수동 워크플로 실행으로 한다. 입력은 장애 이슈 번호이다. 결과는 장애 이슈 대신 별도 검증 이슈에 쓰고, 되돌리기 PR은 만들지 않는(dry-run) 모드로 실행한다. 1.2의 성공 기준과 비교한다. #66의 실패 원문은 #74 이전 기록이라 이슈에 없다. 재생에서는 해당 스모크 run 로그에서 원문을 수동으로 채운 입력을 쓴다.

실제 장애 검증은 기존 실패 주입(`factory-smoke.yml`의 `api_base` 입력)으로 한다. 이 주입에는 원인 PR이 없으므로 분류가 외부 요인이고 되돌리기가 일어나지 않는지 확인한다. 봇 PR 회귀의 실제 검증은 일부러 스모크를 깨는 T1 데모 이슈를 만들어 진행한다. 이 데모의 절차는 운영 문서(`docs/operations.md`)에 추가한다.
