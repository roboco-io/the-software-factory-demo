- 작성일: 2026-10-21
- 상태: 설계 검토 대기. 구현에 착수하지 않았다.
- 기준 코드: `422aa1d` (main)
- 관련 저장소: 책 집필 저장소 [`roboco-io/the-software-factory`](https://github.com/roboco-io/the-software-factory)

## 1. 목적

현재 예제 서비스는 Medium을 흉내 낸 RealWorld(Conduit) 앱이다. 사용자는 글을 쓰고, 댓글을 달고, 다른 사용자를 팔로우한다. 이 서비스를 책 『The Software Factory』의 내용을 두고 토론하는 포럼으로 바꾼다. 독자는 책의 특정 장과 절을 대상으로 토론을 열고, 다른 독자와 스레드 형태로 의견을 주고받는다. 사람뿐 아니라 에이전트도 같은 포럼에 읽고 쓸 수 있어야 한다.

이 전환은 데모의 목적과도 연결된다. 데모는 팩토리가 요청을 받아 서비스를 바꾸는 과정을 보여 준다. 따라서 전환 작업 자체를 팩토리 이슈로 나누어 처리하고, 그 기록을 책의 사례로 쓸 수 있게 한다.

## 2. 사용자가 정한 사항과 이 문서의 가정

사용자가 2026-10-21에 정한 사항은 다음과 같다.

| 항목 | 결정 |
|---|---|
| RealWorld API 계약 | 폐기한다. 포럼에 맞는 새 API를 설계한다. |
| 책과의 연결 | 책이 계속 개정되므로 그에 맞는 연결 방식을 제안받는다. |
| 토론 기능 | 답글에 답글(스레드), 질문·논점 유형 구분, 답글 추천과 정렬, 최근 활동순 목록이 필요하다. 에이전트용 인터페이스도 검토한다. |
| 진행 방식 | 기획 이슈를 열고 팩토리 하위 이슈로 나누어 진행한다. |

다음은 이 문서가 둔 가정이다. 검토 중에 바뀔 수 있다.

- 기존 계정은 유지한다. 기존 글과 댓글은 책 연결이 없는 일반 토론으로 옮긴다.
- 읽기는 로그인 없이 가능하고, 쓰기·추천은 로그인한 계정만 가능하다.
- 팔로우, 즐겨찾기, 개인 피드는 포럼의 성공 기준에 필요하지 않으므로 새 API에 넣지 않는다.
- 사이트 이름 conveyor와 이미지 업로드, 피드백·에러 수집 경로는 그대로 둔다.

## 3. 책과의 연결 방식

### 3.1 문제

책은 공개 초안 상태이며 계속 고쳐진다. 2026-10-21 기준으로 `manuscript/chapters`에 대한 커밋이 21건 있다. 절 제목이 바뀌거나 절이 합쳐지고, 장 순서가 바뀔 수 있다. 토론을 장 번호나 절 제목 문자열에 연결하면 개정 후에 링크가 엉뚱한 곳을 가리키거나 끊어진다. 반대로 토론 시점의 본문을 복사해 두면 포럼이 책의 사본을 관리하게 되고, 개정된 본문과 어긋난다.

### 3.2 책 저장소에 이미 있는 장치

책 저장소의 `website/content-manifest.json`은 문서마다 `revision`(개정 번호)과 `anchors`(절 제목 → 고정 앵커 ID)를 기록한다. 예를 들어 `ch01`의 두 제목 "더 빨리 만든 뒤에도 남는 문제"와 "고객의 문제와 사업 성과를 개발의 기준으로 삼는다"는 같은 앵커 `s01`을 가리킨다. 즉 제목을 바꿔도 앵커는 유지된다. 책 사이트는 이 앵커를 HTML `id`로 출력한다(`https://factory.roboco.io/book/ch05/#s03`). 매니페스트에는 45개 문서(머리말, 20개 장, 패턴, 데모 해설 등)가 있다. 2026-10-21에 GitHub API와 책 사이트에서 확인했다. 매니페스트는 사이트에서 직접 내려받을 수 없고(404), 저장소 파일로만 공개되어 있다.

### 3.3 제안: 고정 앵커 + 개정 번호를 함께 기록한다

토론은 `(문서 ID, 앵커 ID)`에 연결하고, 토론을 연 시점의 문서 `revision`을 함께 저장한다. 예를 들어 `(ch05, s03, revision 7)`이다. 이렇게 하면 다음 세 상황을 구분해서 보여 줄 수 있다.

| 상황 | 판정 기준 | 포럼 표시 |
|---|---|---|
| 본문이 그대로다 | 현재 revision이 토론 시점과 같다 | 표시 없음 |
| 토론 이후 장이 개정됐다 | 현재 revision이 더 크다 | "이 토론 이후 책이 개정됨" 배지와 책 링크 |
| 절이 사라졌다 | 앵커가 현재 매니페스트에 없다 | "현재 판본에 없는 절" 배지. 토론은 장 단위로 계속 보인다 |

revision은 장 단위 번호이므로 같은 장의 다른 절이 바뀌어도 배지가 뜬다. 절 단위 변경 여부는 현재 매니페스트로 알 수 없다. 정확도를 높이려면 책 저장소가 절별 해시를 매니페스트에 추가해야 한다. 이는 책 저장소 쪽 변경이므로 이 설계의 범위 밖에 두고, 장 단위 배지로 시작한다.

포럼은 책 본문을 저장하지 않는다. 장 제목과 절 제목, 앵커, revision만 동기화한다. 본문은 항상 책 사이트 링크로 연다.

### 3.4 동기화

API Worker에 Cloudflare Cron Trigger를 추가한다. Cron은 하루 몇 차례 `raw.githubusercontent.com`에서 매니페스트를 받아 `book_documents`·`book_sections` 테이블을 갱신한다. 장 제목은 매니페스트에 없으므로 각 장 마크다운의 첫 `#` 제목을 함께 읽는다. 동기화가 실패하면 기존 데이터를 그대로 두고 에러 수집 경로(`error-events`)로 기록한다. 포럼은 마지막 동기화 시각을 화면에 보여 준다.

책 사이트의 각 절에 "이 절 토론하기" 링크를 넣는 작업은 책 저장소의 변경이다. 포럼은 `#/new?doc=ch05&anchor=s03` 형태의 진입 주소만 제공하고, 책 사이트 변경은 책 저장소에 별도로 요청한다.

## 4. 포럼 모델과 API

### 4.1 데이터 모델

| 테이블 | 역할 | 주요 열 |
|---|---|---|
| `users` | 기존 계정. 에이전트 계정도 포함 | 기존 열 + `kind`(`human`/`agent`), `owner_id`(에이전트를 등록한 사람) |
| `book_documents` | 책 문서 목록 | `doc_id`(`ch05`), `title`, `revision`, `synced_at` |
| `book_sections` | 절과 고정 앵커 | `doc_id`, `anchor`(`s03`), `heading`, `active` |
| `topics` | 토론 주제 | `title`, `body`, `kind`(`question`/`argument`/`case`/`general`), `author_id`, `doc_id`, `anchor`, `book_revision`, `reply_count`, `last_activity_at` |
| `replies` | 답글 | `topic_id`, `parent_id`(없으면 최상위), `body`, `author_id`, `score` |
| `reply_votes` | 답글 추천 | `(user_id, reply_id)` 기본키. 한 사람이 한 번만 추천 |

`kind`의 의미는 다음과 같다. `question`은 책 내용에 대한 질문, `argument`는 책의 주장에 대한 반론이나 보완, `case`는 자기 조직의 사례 공유, `general`은 그 밖의 토론과 이전 데이터다.

답글은 깊이 제한 없이 저장하되 화면에서는 4단계까지만 들여쓰고 그 이후는 같은 깊이로 보여 준다. 저장 구조에 제한을 두지 않는 이유는 표시 정책을 나중에 바꿔도 데이터를 옮길 필요가 없게 하기 위해서다.

### 4.2 API 개요

오류 형식은 기존 규칙 `{"errors": {"field": ["message"]}}`와 `apps/api/src/lib/errors.ts` 헬퍼를 유지한다. 인증은 기존 JWT를 쓰고, 에이전트는 별도 API 토큰을 쓴다(5장).

| 메서드·경로 | 설명 |
|---|---|
| `GET /api/book` | 문서 목록, 문서별 토론 수, 마지막 동기화 시각 |
| `GET /api/book/:docId` | 절 목록과 절별 토론 수 |
| `GET /api/topics?doc=&anchor=&kind=&sort=activity\|new&limit=&offset=` | 토론 목록. 기본 정렬은 최근 활동순 |
| `POST /api/topics` | 토론 생성. `doc`·`anchor`는 선택. 지정하면 현재 revision을 함께 저장 |
| `GET /api/topics/:id` | 토론과 책 연결 상태(그대로/개정됨/사라진 절) |
| `PUT`·`DELETE /api/topics/:id` | 작성자만 수정·삭제 |
| `GET /api/topics/:id/replies?sort=top\|old` | 답글 트리 |
| `POST /api/topics/:id/replies` | 답글 작성. `parentId`로 답글에 답글 |
| `PUT`·`DELETE /api/replies/:id` | 작성자만 수정·삭제. 하위 답글이 있으면 본문만 "삭제됨"으로 바꾼다 |
| `POST`·`DELETE /api/replies/:id/vote` | 추천과 취소 |

`users`, `user`, `profiles/:username`, 이미지·피드백·수집 경로는 기존 것을 유지한다. `articles`, `comments`, `tags`, `favorite`, `follow`, `feed` 경로는 6장의 전환 마지막 단계에서 제거한다.

### 4.3 화면

| 화면 | 내용 |
|---|---|
| 홈 | 최근 활동순 토론 목록과 책 목차(장별 토론 수) |
| 장 화면 | 절 목록, 절별 토론, 책 원문 링크, 개정 배지 |
| 토론 화면 | 본문, 책 연결 상태, 스레드 답글, 추천순/시간순 정렬 |
| 토론 작성 | 장·절 선택, 유형 선택. 책 사이트에서 넘어오면 장·절이 미리 채워짐 |
| 프로필 | 작성한 토론과 답글. 에이전트는 배지와 등록한 사람을 표시 |

마크다운은 기존 규칙대로 `renderMarkdown()`으로만 렌더링한다.

## 5. 에이전트 인터페이스

사람과 에이전트가 같은 토론에 참여하되, 독자가 둘을 구분할 수 있어야 한다. 그리고 에이전트의 글에는 책임질 사람이 있어야 한다. 이를 위해 다음을 제안한다.

첫째, 에이전트 계정을 둔다. 로그인한 사람이 `POST /api/agents`로 에이전트를 등록하면 `kind=agent`, `owner_id=등록자`인 계정과 API 토큰이 발급된다. 토큰은 발급 시 한 번만 보여 주고 해시만 저장한다. 에이전트의 모든 글에는 화면과 API 응답 모두에 에이전트 배지와 등록자가 표시된다. 등록자는 토큰을 폐기할 수 있다. 에이전트 계정에는 사람 계정보다 낮은 쓰기 빈도 제한을 둔다.

둘째, 기계가 읽을 수 있는 설명을 제공한다. `GET /api/openapi.json`에 API 명세를, 웹 루트의 `llms.txt`에 포럼의 목적, 책과의 연결 규칙, 에이전트 참여 규칙(출처 표시, 책 앵커 지정, 사람 행세 금지)을 둔다.

셋째, MCP(Model Context Protocol) 서버는 2단계로 미룬다. MCP 서버를 두면 Claude 같은 에이전트가 도구 호출로 토론을 읽고 쓸 수 있다. 다만 REST API와 OpenAPI만으로도 에이전트가 참여할 수 있으므로, 실제 사용 요구가 확인된 뒤에 추가한다. 추가할 때는 같은 Worker에 원격 MCP 엔드포인트를 두고 REST API와 같은 인증·빈도 제한을 공유한다.

에이전트 계정 등록과 토큰 발급은 인증 경계이므로 T2로 다룬다.

## 6. 전환 전략과 팩토리 검증 체계

### 6.1 왜 단계적으로 바꾸는가

RealWorld 공식 Hurl 스위트(`tests/realworld/vendor/`)는 필수 체크 `realworld-api`로 모든 PR에서 실행된다. 이 스위트는 팩토리 봇이 구현의 완료를 판정하는 기준이고, 봇이 약하게 만들지 못하도록 T3 경로로 보호된다. 계약을 한 번에 폐기하면 봇이 무엇을 기준으로 구현해야 하는지가 사라진다.

그래서 기존 저장소의 방식을 그대로 따른다. 사람이 새 포럼 계약 테스트를 먼저 작성해 보호 경로에 두고, 아직 구현되지 않은 파일은 건너뜀 목록에 올린다. 팩토리 봇은 하위 이슈마다 기능을 구현하고 건너뜀 목록에서 해당 파일을 지운다. 이는 RealWorld 스위트에서 `skip.txt`를 쓴 방식과 같다. 새 기능이 모두 통과하면 마지막에 RealWorld 경로와 스위트를 제거한다. 이 기간에는 RealWorld API와 포럼 API가 함께 동작한다.

### 6.2 사람이 먼저 해야 하는 T3 변경 (0단계)

다음 변경은 T3 경로라서 팩토리 구현 에이전트가 수정할 수 없다. 저장소 소유자 또는 소유자가 지정한 로컬 실행자가 PR로 만들고 CODEOWNERS가 승인한다.

- `tests/forum/*.hurl`: 포럼 계약 테스트. 4.2의 각 경로에 대해 정상·오류·권한 케이스를 쓴다. 계약 테스트는 이 설계 문서가 승인된 뒤 작성한다.
- `tests/forum/skip.txt`와 `scripts/forum-api.sh`: 기존 `scripts/realworld-api.sh`와 같은 방식의 실행 스크립트.
- `.github/workflows/ci.yml`: `forum-api` 체크 추가.
- `factory/risk-policy.yml`: `requiredChecks`에 `forum-api` 추가, `tests/forum/**`를 T3에 추가. `.github/CODEOWNERS`도 함께 갱신.
- `factory/prompts/*.md`, `AGENTS.md`: RealWorld 언급을 포럼 계약 기준으로 바꾼다.
- `apps/web/e2e-smoke/home.spec.ts`: 웹 스모크를 RealWorld 화면 문구에서 분리한다. 6.3절의 0단계 변경이다.

### 6.3 프로덕션 스모크의 전환 순서

2026-10-21 기준 스모크는 두 파일이다. `tests/smoke/readonly.hurl`은 `GET /health`, `GET /articles?limit=1`, `GET /tags`를 확인한다. `apps/web/e2e-smoke/home.spec.ts`는 홈 화면에서 제목 `conveyor`, 문구 "Global Feed", 로딩 완료, 오류 없음, 피드백 버튼을 확인한다. 이 스모크는 세 곳에서 실행된다. 봇 PR의 프리뷰(`smoke-preview`, T0·T1 자동 병합의 조건), 배포 직후(`deploy.yml`), 6시간마다 도는 프로덕션 점검(`factory-smoke`)이다. 두 파일은 T3라서 봇이 고칠 수 없다. 프로덕션 스모크가 실패하면 자동 포스트모템이 시작되고, 조건을 충족하면 원인 PR을 되돌린다.

그대로 두면 두 시점에서 스모크가 깨진다. 3단계에서 홈 화면을 바꾸면 "Global Feed" 문구가 사라져 봇 PR의 프리뷰 스모크가 실패하고, PR이 사람에게 넘어간다. 5단계에서 RealWorld 경로를 지우면 `/articles`와 `/tags` 검사가 실패한다. 이 PR이 먼저 병합되면 PR #65 때처럼 프로덕션 스모크가 깨진다. 당시에는 약 7일간 스모크가 실패했다(#66, #81).

그래서 스모크는 "넓히기 → 옮기기 → 줄이기" 순서로 바꾼다. 스모크는 항상 프로덕션에 이미 배포된 계약만 확인하고, 스모크가 의존하는 경로는 스모크에서 먼저 뺀 뒤에 지운다.

| 시점 | 스모크 변경 | 수행 | 선행 조건 |
|---|---|---|---|
| 0단계 | 웹 스모크의 "Global Feed" 검사를 고정 표식 `data-testid="smoke-ready"`(주 목록 로딩이 끝나면 나타남) 검사로 바꾼다. 제목·오류 없음·피드백 버튼 검사는 유지한다. 현재 홈에 표식을 추가한다. | 사람 | 없음 |
| 3단계 | 스모크 파일은 바꾸지 않는다. 새 홈 화면 하위 이슈의 완료 기준에 "`smoke-ready` 표식과 피드백 버튼을 유지한다"를 넣는다. | 팩토리 | 0단계 병합 |
| 1·2단계 배포 후 | Hurl 스모크에 `GET /book`, `GET /topics?limit=1`을 추가한다. 토론이 0건이어도 통과하도록 응답 형식만 검사한다. | 사람 | 해당 기능의 프로덕션 배포 확인 |
| 5단계 직전 | Hurl 스모크에서 `/articles`, `/tags` 검사를 뺀다. | 사람 | 포럼 경로 스모크가 프로덕션에서 통과 |
| 5단계 | RealWorld 경로 제거 PR을 진행한다. | 팩토리 + 사람 | 위 스모크 축소 PR 병합 |

전환을 시작하기 전에 열린 스모크 장애 이슈를 정리한다. 2026-10-21 기준 #66은 2026-10-20 21:41(UTC) 실행부터 스모크가 다시 통과했지만 열려 있다. 전환 중의 스모크 실패와 섞이지 않게 하기 위해서다.

### 6.5 완료 기준

- `forum-api` 체크가 건너뜀 없이 통과한다.
- RealWorld 경로와 `tests/realworld/`가 제거되고, 필수 체크에서 `realworld-api`가 빠진다.
- 프로덕션에서 책 장·절 목록이 매니페스트와 일치하고, 개정 배지가 3.3의 기준대로 표시된다.
- 에이전트 계정으로 쓴 토론과 답글에 배지와 등록자가 표시된다.
- 전환 기간 동안 전환 작업이 원인인 프로덕션 스모크 실패가 없다.
- 각 하위 이슈가 팩토리 절차(구현 → 교차 리뷰 → 검사 → 병합 → 배포)를 거쳐 닫힌다.

## 7. 열린 질문

- 신고·숨김 같은 운영(모더레이션) 기능이 첫 공개에 필요한가. 이 설계에는 넣지 않았다. 에이전트 참여를 허용하면 필요성이 커진다.
- 책 저장소에 절별 해시를 추가해 개정 배지를 절 단위로 정확하게 만들 것인가.
- 포럼과 책 저장소 이슈(독자 피드백 경로)의 관계. 토론에서 나온 개정 제안을 책 저장소 이슈로 넘기는 경로는 이 설계에 없다.
